# 30分区間の逐次会計

最初に [監査結果.json](監査結果.json)、次に [時間区間損益.json.gz](時間区間損益.json.gz) を見る。後者はUTF-8 JSONをgzipで圧縮した表示元データ。11方式・506口座・10,252区間を保存し、88件の途中切断で現在までの口座状態が一致した。

日本時間の00分/30分で区切る。日中の最初だけ08:45〜09:00。区間は開始を含み終了を含まない。

- 確定利益・確定損失・確定収支: その区間で返済した売買の損益。
- 終了含み: 区間端より前の最後の価格で残玉を評価した金額。
- 含み増減: 終了含み − 開始含み。
- **時価収支: 確定収支 ＋ 含み増減。** 損益を返済区間だけへ寄せず、その時間帯の値動きによる口座増減を示す。
- 新規件数・返済枚数: その区間に成立した注文から数える。

全区間の時価収支合計と確定収支合計は、元台帳の場収支へ一致する。場末の建玉・含みはゼロ。TOPIX miniは片方向上限10枚、NK225 microは20枚として検査する。

`replay_intervals.py` の `IntervalAccount.on_event` は現在行の時計・価格・成立約定だけを受け取る。未来の配列を口座内に保存しない。同時刻でも原本行順を保持し、端点を未来価格で補間しない。既存台帳の会計監査であり、シグナルを作り直すエンジンではない。

原本の `CurrentPriceTime` は最後の約定時刻で、実際の板受信時刻ではない。受信遅延や注文遅延の正確な再現はこの区間会計の対象外。

今回代表11方式をまとめて再実行:

```text
python -X utf8 work/wave_v51/interval_audit/run_all.py
```

`replay_intervals.py` を単独で引数なし実行するとE01/O03の2方式だけを再生成する。追加台帳は `--include 手法名=台帳パス` を繰り返し指定する。E01型8列と独立96方式・注文方式型10列を共通会計へ変換できる。両建ては買い玉・売り玉を別管理し、利益玉だけでなく両脚を合算する。

## E01赤字時間帯から分かったこと

[E01赤字区間比較.json](E01赤字区間比較.json) は、E01の結果を見て赤字／黒字／同値区間へ分けた事後説明用資料。注文条件や候補選択には使用していない。

既知追加4場で、連敗休止O03はTOPIXのE01赤字区間を140,000円改善した一方、E01黒字区間を43,500円削ったため、差は96,500円の改善。NK225は赤字区間を26,800円改善したが、黒字区間を37,600円削り、10,800円の悪化になった。

時計修正K20のTOPIXは赤字区間を83,500円改善しても、黒字区間を157,500円削り、E01が同値だった時間帯でさらに11,000円損失を出した。悪い時間帯の回避だけでは改善を判断できず、回復時間帯や新しいエントリーによる損益も同時に確認する必要がある。
