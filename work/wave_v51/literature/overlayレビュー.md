# E01 重ね合わせ32条件の独立レビュー

対象: `work/wave_v51/overlay/research.py`、`条件固定.json`、`選択結果.json`。実施日: 2026-10-07。対象実装は変更していない。現在 API の取得なし。

## 判定

**重ね合わせ方式として、今回の入口選択と損益状態の更新に未来損益の混入は見つからなかった。ただし、O03 は両銘柄の連敗問題を解決していない。新4場の NK225 は従来より悪化しており、本採用の根拠としては足りない。**

## 独立確認したこと

`check_overlay.py` は、組を順に処理する元実装とは別に、「注文計画の源行」「組の全返済行」を時系列イベントに展開した。損益は全返済行に達したときだけ公開し、次の入口を判定した。

- **32条件 × 46口座 = 1,472比較**で、選択組数・収支・累積Rが元実装と一致した。
- **7,520件**の計画源行について過去損益だけを使うことを確認した。条件違いによる重複を含む。
- 全組で、計画源行 < 新規約定行 <= 最終返済行を確認した。
- 原研究器が要求する「前組返済行 < 次組の計画源行」が成立する。そのためコードが計画の直後に当該組の将来損益を状態へ足していても、それを使う次の判定は返済後だけであり、順序短縮として等価である。
- 組損益は返済脚の合計と一致した。Rの分母は初回枚数 × 入口時に固定されたATRと一致した。
- 同一 CurrentPriceTime 内でも原本行順は区別されている。時刻だけの厳密大小ではなく、行順による後続約定という前提である。

結果: [overlay独立会計.json](overlay独立会計.json)。指標計算と元 E01 仮想エンジンは既存実装を利用しており、それらすべてを独立再実装した監査ではない。

## 実装可能だが、仕様に明記すべき点

1. **仮想 E01 を休止しない。** 実口座で見送った組も影口座では最後まで運転する。実口座の入口・決済を変えた結果で、次の仮想組の時計を作り直さない。通常の「E01 にフィルタを足した実口座」と同じではない。
2. **計画更新行で許可を判定する。** 保存台帳の `orders[:,1]` は最終的な計画源行であり、最初の追跡準備開始行や条件成立行とは異なる。リアルタイムでは影口座の各計画更新を購読し、直前に許可した実注文も、後続の不許可更新で取り消す／差し替える必要がある。将来約定する計画を事後に選ぶだけの実装にはしない。
3. **45分経過は即再開を意味しない。** 休止中に影口座が建てた仮想組がまだ残れば、その組を途中から実口座へ取り込まず、次の仮想組まで待つ。したがって実際の新規空白は45分を超え得る。
4. **損失状態は実口座で採用した全返済済み組だけ。** 見送った仮想勝ち・負けは連敗数にも累積Rにも入れない。半数利確時はまだ更新せず、残りも返済してから組全体で判定する。
5. **TOPIX と NK225 は別口座の休止。** 二市場を合算した連敗やRではない。ゼロ損益の組は連敗を切る。ここも規則として固定する。
6. **day2R は当場損失を2R以下に保証するものではない。** 全返済時に累積Rを確認して新規を止める方式であり、現在組の含み損や、閾値をまたぐ最終損失は抑えない。

O03 の新4場黒字率は両銘柄とも **1/4場**で、従来と同じ。平均の勝ち1枚/負け1枚比が2以上でも、勝つ頻度が不足すれば赤字になる。NK225では休止により回復の勝ちを落とした影響が勝っている。

したがって「連敗後に休むと安全」「損小利大なので安定」という一般結論には反証がある。TOPIX の損失抑制候補とは言えるが、二市場共通の問題解決として扱わない。

## 追加すべき反証

- 連敗閾値2の近傍1/3、休止45分の近傍30/60分で成績が連続的か確認する。一点だけ改善なら過剰適合を疑う。
- 同じ時間・同じ回数だけ無作為に休む対照を作り、連敗情報に追加価値があるか分ける。
- 影口座全イベントを逐次実行する入口ラッパーを実装し、許可更新・取消・未約定更新も含む注文列を保存台帳による選択結果と照合する。現監査は完成した組の因果順序確認までである。
- 新規計画更新から約定まで長い場合、許可根拠が古くなる。計画時許可と条件成立時再確認を別候補として比較する。後者は実トレールの注文方法まで変えるため、現32候補と混ぜない。
- 当該組の将来損益を改変しても、その組の入口許可が変わらないことを逐次エンジンで確認する。
- 既存テストの未来指標改変は `snapshot` の参照索引の検査である。元の足データの将来部分を改変して全指標を再計算する検査も加えると、特徴量生成自体の因果性まで確認できる。

## 表示上の注意

`選択結果.json` の「全合格」は実装確認の合格を指す。戦略としての合格や将来収益の証明とは分けて表示する。追加4場だけでなく全23場も過去の探索で既読のため、新方式にとって真正な未見ではない。
