# 保存D07の利益返しと追加玉

**少枚数で利益を返す問題は過去にも存在する。一方、追撃玉を一律になくすと利益も失う。**

00145の保存50場（25昼・25夜）、日経mini換算・上限10枚・手数料0。266親・367玉を独立会計し、全場の利益・損失・収支が元会計と一致。累計は利益7,689,000円、損失3,530,000円、収支4,159,000円。新しい売買再生はしていない。

## 少枚数で利益を返した親

親全体の清算価値は、既に確定した損益と残玉の清算含みの合計。残玉の含みだけの最高値もJSONへ別保存した。少枚数は実保有1〜2枚。将来の最高値を取れる利益と解釈しない。

|担当・時間帯|全親数|1〜2枚で正の清算価値があった親|その後、親全体が赤字|
|---|---:|---:|---:|
|基本CG_Day|60|14|0|
|基本CG_Night|29|22|1|
|追加担当A_Day|45|38|20|
|追加担当A_Night|48|43|21|
|別入口CS_Day|36|31|9|
|別入口CS_Night|48|42|16|

全体では、少枚数で正の清算価値があった190親中67親が最終赤字。追加担当Aは昼38親中20親、夜43親中21親だった。これは当時の最高値を事前判別できたという意味でも、保護開始を早めれば全部救えるという意味でもない。

**10/6デイ：追撃がなくても発生。** 09:36:50にA担当が売2枚70,380。09:56:00に清算含み34,000円まで進んだ後、13:07:50に70,620で全返済して48,000円損失。追撃0なので、追加条件だけの修正ではこの問題は残る。原行は新規20,656、最高28,131、返済82,175。

## 追加玉の利益と損失

『追加担当A』は独立した担当名。以下の『追撃玉』は、どの担当でも同親に保有がある間に増えた新規UIDを指す。2つを混同しない。

|担当・時間帯|追撃玉数|勝ち/負け/同額|追撃玉収支|追加から5分以内に赤字完結|
|---|---:|---:|---:|---:|
|追加担当A_Day|26|18/8/0|-4,000円|1|
|追加担当A_Night|23|11/11/1|93,000円|9|
|別入口CS_Day|21|11/10/0|191,000円|5|
|別入口CS_Night|31|17/12/2|122,000円|4|

全追撃101玉は57勝41敗3同額、利益797,000円・損失395,000円・収支402,000円。追加から1分以内の赤字完結は3玉、5分以内は19玉。短時間の赤字は出口理由を問わない実測であり、全てが価格損切りという分類ではない。

**10/14デイ：追加直後に旧親の損失幅を受ける。** 10:47:23にA担当が売1枚68,060を追撃。既存2枚の清算含みは12,000円あった。追撃玉は最大順行10ptだけで、180秒後の10:50:23、68,250で19,000円損失。新規原行50,664、返済51,892。既存玉の順行と、追加玉自身の有利さは同じではない。

**消す勝ちの例。** 10/20ナイト22:53:21のA追撃1枚64,240は73,000円利益。10/22デイ09:21:07の別入口CS追撃1枚64,580は121,000円利益。追撃禁止で損失玉だけを消した収支を改善効果として示さない。

## 再利用する資料と、現在アプリとの区別

- D07約定：`work/research145_roles/orders/{session}.npz` の `D07`。`research145_report/combined_orders` はC01〜C03用なので使用しない。
- 保存会計：`work/research145_roles/役割分離の全場結果145.json`、最終報告は `work/research145_report/report145.json`。
