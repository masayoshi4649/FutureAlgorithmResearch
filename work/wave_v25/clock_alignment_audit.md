# 時刻群と両市場の対応監査

既存の処理は、同じ `CurrentPriceTime` の全行を集計し、**次の異なる時刻の先頭行**で特徴を解放していた。今回疑った「相手原本の同時刻末尾へ飛んで未完了群を読む」不具合は検出されなかった。

- 原本 2,931,845 行中、直前行と同じ記録時刻の遷移は 2,824,419 件。
- 解放特徴 106,451 行は時刻が厳密昇順。同時刻重複 0 件。
- 解放seqが次の時刻群の先頭有効行でない件数 0 件。素材群の次異時刻と解放時刻の不一致 0 件。
- 素材終端seqが解放seq以前に完結していない件数 0 件。素材時刻が解放時刻以上の件数 0 件。
- 60秒遅延の相手参照が可能な 105,807 判断点で、素材と解放の順序違反 0 件。

`_book` / `_board` の `time_s` は素材時刻ではなく解放時刻であり、相手側の後方参照は一群一行の確定した特徴に対して行われる。現在最良気配を使う列も、解放時刻群の末尾ではなく先頭の気配を使用している。

なお受信タイムスタンプは存在しない。**各市場の記録順で因果的であることと、二市場の実受信順が一致することは別である。** 60秒遅延は保守的な余裕だが、実際の遅配上限を保証する証拠ではない。原本の将来部分を削るprefix監査だけでは、この計測上の制限は解消できない。

参考として、解放後さらに一群待つと相手参照点は 104,876 / 106,451 判断点で変わる。これは既存バグ修正ではなく追加遅延感度であり、今回の選別基準には加えない。各入力の待ち時間と件数は JSON を参照。現在API取得・旧コード変更・売買損益参照は行っていない。
