# 管理比較用の共通入口

最初に `共通入口スケジュール仕様.json` を読み、次に `共通入口スケジュール検査.json` を確認する。入口の内容は `入口仕様.json`、旧入口の再生成は `旧入口部品の再生成検査.json` に記録している。

## 親管理器からの呼び出し

`schedule.pkl` は `dict[(セッション名, 銘柄名)] → list[6つのndarray]`。順序は `T1L1、T2L0、T3L1、T4L0、E01P、R01P`。各配列は形状 `(初回数, 5)`、列は次の順序。

1. `fill_i`：初回約定の原本行番号
2. `decision_i`：逆指値成立・発注判断の原本行番号
3. `source_i`：入口候補による親予約の原本行番号
4. `side`：買い `1`、売り `-1`
5. `anchor`：親予約時の買い気配ask又は売り気配bid

3種類の行番号は数値配列の都合でfloat64だが整数値であり、インデックス使用時にintへ変換する。初回約定価格は `fill_i` の買いask／売りbidであり、`anchor` とは区別する。

初回fill後は3600秒＋30秒の共通枠を設ける。管理方法が早く返済しても、その枠内に別の初回を増やさない。これは途中管理そのものの比較用であり、旧v69の通し運用や旧E01/R01の完全再現ではない。

`signals.pkl` は同じkeyに対応したint8配列 `(6, 原本行数)`。`levels.pkl` は旧E01入口stateと、R01のEMA確認を加えたstateの2行。いずれも新規・返済台帳を参照せず、パルス又は方向を作る。最大保有TOPIXミニ10枚／NK225マイクロ20枚と実際の途中管理は親管理器が担当する。

## 凍結結果

全28セッション・56口座の共通初回数は、上記の順に192、413、51、495、406、397。少ない入口も損益を見て外していない。

入力配列・原本順・時計・ATRは既存v69入力と完全一致。共通入口336系列の途中切断・未来改変で過去の約定が変わらないこと、予約行＜成立行＜約定行、初回間隔3630秒以上を確認した。原本末尾の未成立予約／成立済み未約定を未来の情報で取り消す処理はない。

`check_original.py` は旧E01の入口生成器で全56口座のstateを再生成して一致させ、保存素材を中間で切断した結果も照合する。R01の追加EMA確認は旧生成器と全長一致。旧ティック4系列はv69の凍結済み入口とその因果検査をそのまま再利用する。

現在API、注文API、旧取引台帳、新しい管理損益は参照していない。原本と旧作業は書き換えていない。

## 再生成

`prepare.py` と `schedule.py` は完了済み出力がある状態では上書きしない。新しい入力作業で再生成する場合も同じく入口規則を先に固定し、損益の採点後に書き換えない。

旧入口を独立再照合する場合は、ルートから `python -X utf8 work/wave_v70/inputs/check_original.py` を実行する。
