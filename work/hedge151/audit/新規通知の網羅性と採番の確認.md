# 新規通知の網羅性と採番の確認

2026-10-27。金融再生0。保存B04の全26ケースと、日経10/21ナイトの原板1本の技術走査だけを実施した。新しい売買判断・損益の測定ではない。

## 約定済み一覧から通知を読むことの確認

今回の保存B04については、実約定一覧に保存された新規通知を利用しても、未約定の新規通知を将来の約定可否で除外しないことを、以下のコード経路と保存状態から確認した。

1. `preus150/engine_go_round2/main.go::process` は `Portfolio.Observe` の返した全通知を無条件で `Case.Pending` へ追加する。
2. 次の正常BBOで `Case.Pending` 全件を処理する。各通知は `OnFill`、`OnOrderDone`、保存Eventへの追加を通り、価格・黒字赤字による採用条件はない。正常気配が来ない間はPendingを維持する。
3. 時間帯切替の `Pending=nil` は `flat(Portfolio)` 成立後のみ。`researchStatus` はDoneでない全注文をPendingへ返すため、未約定通知が残る状態で切り替えて消す経路はない。
4. 各位相で `emitResearch` は通知ごとに連番を1増やす。全26保存の381注文で位相別の連番が1から欠けずに並び、同じIDの重複はない。
5. 末尾 `FinalPending` は途中の10/26を含む全26ケースで空。全173新規の担当別件数も保存診断の実新規数と一致した。

したがって今回の26ケースには、保存されていない末尾未約定や、約定結果によって消されたB04発注判断は確認されない。宣言だけで増えない `CancelledNew=0` を証明には使っていない。

これは**B04が発注を決めた通知の再利用**である。B04自身の保有上限や内部判断で元から発注されなかった全候補を、別の実玉管理に合わせて新たに生成する方式ではない。仮想B04の損切り・保有・利確が将来の通知機会へ作用する点は仕様として残る。

## source_indexはファイルの行番号ではない

旧 `loadBoards` は時計欠測・範囲外・時計逆行・非正または非有限Lastを採用前に除く。一方、異常BBOは採用列から除去しない。その列を時刻で安定結合し、`Features.OnBoard` の市場別 `Counts[reference]` を0から採番する。同じ時計にTOPIX行が入っても日経のカウンタは増えない。

日経2026-10-21ナイトを別の読取コードで走査した結果は、原181,379行・時計欠測360行・範囲外11行・採用181,008行で保存値と一致。前後半の全新規について、採用添字、判断時刻、Last、bid、askが保存証拠と一致した。例えば19:13:19の売りの添字30,812は原ファイルの単純な30,813行目を意味しない。

今回の独立実測照合は原板1場であり、全26原板を再走査した検証ではない。特徴量そのものも再計算していない。新しい00151の原板読込がこの採番と一致するかは、実装完成後に別途同じ保存期待を使って検査する。
