# 共通知見台帳

最初に **[知見台帳](index.html)** を開いてください。ローカルファイルのまま、サーバーを起動せず閲覧できます。

読む順序は「知見」→「重複点検」→気になる手法の「試行」です。「過去資料」は00001〜00100への索引です。資料の存在確認と、全条件の同一性の監査完了は区別しています。

## データとビュー

| 場所 | 役割 |
| --- | --- |
| `data/knowledge.json` | 確認済み知見・未検証仮説・適用範囲・次の判断・根拠の正本。 |
| `data/trials.json` | 試行条件・状態・結果・変更点・再検証理由・重複点検の正本。 |
| `data/studies.json` | 過去作業の資料索引の正本。 |
| `index.html`、`view/app.js`、`view/style.css` | 数値や結論を持たない共通ビュー。 |
| `data/view-data.js` | JSONから自動生成する閲覧専用データ。直接編集しない。 |
| `manage.py`、`duplicate_check.py` | 整合検査・閲覧データ生成・試行の事前照合。売買を実行しない。 |

正本を更新したら、プロジェクトルートで次を実行します。

```text
python -X utf8 アルゴリズム調査/共通/知見台帳/manage.py build --deep
python -X utf8 アルゴリズム調査/共通/知見台帳/manage.py verify --deep
```

`view-data.js`は、file方式でJSONの非同期読込が制限される環境でも閲覧するための生成物です。`verify`で正本と生成物が完全に一致することを確認します。知見の追加だけならHTML・JS・CSSの変更は不要です。

## 同じ試行を繰り返さない手順

1. 台帳で、手法名だけでなく「再参加」「利益追尾」「配分」など思想・部品でも検索する。
2. 保存済みの条件・失敗理由・根拠を読む。過去の否定はその条件と期間に限り、技法全体の否定に拡張しない。
3. 新計画をJSONで作り、入口・途中判断・出口・枚数と配分・費用・約定・対象データ・実装版の8部品を記録する。
4. 事前照合し、「前回から何が変わり、何を確かめるか」を登録してから金融再生する。
5. 結果、反証、避けた損失と失った利益を同じ試行へ追記する。入力不備や実装失敗は、アルゴリズムの成績と分ける。

```text
python -X utf8 アルゴリズム調査/共通/知見台帳/manage.py check --proposal work/新計画.json
python -X utf8 アルゴリズム調査/共通/知見台帳/manage.py register --proposal work/新計画.json
```

新計画の型は [proposal.sample.json](proposal.sample.json) を参照してください。空欄を残したまま登録できません。8部品内には実行条件だけを置き、表示名・説明・結果は`spec`の外へ置きます。実装版は実際のソースSHA256、データは使用ファイルを特定できる目録SHA256と対象セッションを含めます。

`spec.data.input_manifests` は `{"path":"ルートからの目録パス","sha256":"64桁"}` の配列、`spec.data.sessions` は重複しない場名の配列です。`spec.implementation` は `{"ルートからのソースパス":"64桁SHA256"}` とします。登録前と `verify --deep` で、実在する目録・ソースの内容に一致するか照合します。

完全一致の既存実績は再利用します。独立再検証が必要な場合は、比較元IDと理由を付けて別試行として登録します。新データ、実装修正、条件変更はそれぞれ別扱いです。**再描画・再集計・同値確認を、新しい相場での成功例に数えません。** 登録コマンドは金融処理を起動しません。

一致判定は明示された仕様の比較です。実装が違っても論理的に同じ場合や、過去の条件が未整理の場合は自動判定だけでは足りません。未整理の試行がある限り「重複なしを証明した」とは扱いません。
