# S01移植の独立照合

これは新しい売買条件の探索ではなく、研究00154のS01を実アプリへ移した際の挙動照合である。原資料への再生は、00155の試行登録成功と実装指紋固定の後に限る。実APIへの接続・発注はしない。

## 固定対象

- 00154の保存入力を変更せず再利用する。完了51場はDay26・Night25、別枠に2026-10-27 Dayの12:08までの途中1場を置く。
- 日中27場はS01とD07、夜間25場はD07を照合する。合計52資料・79条件場。途中は強制清算せず、実現・含み・残玉・未約定を比較する。
- D07の期待値は `work/d07_154/results_go` のD07、S01は `work/d07_154/results_round2` のS01。保存結果は読取り専用であり、その利益や将来返済を売買判断へ渡さない。
- 日経mini・片方向10枚、5/3/2担当配分、手数料0、ラージの次の正常BBOを用いる。現アプリの任意商品・部分約定・通信障害は別の人工検査に分ける。
- 新規起動と同じく新しいPortfolioを用いる。共通Featuresを同じ観測順で作り、影運転はS01内部の独立D07が逐次進める。将来の影親終了時刻を渡さない。

## 照合内容

`replay_go` の独立プログラムは実アプリの `internal/strategy`・`rules`・`e01` と対象ルールを固定コピーして呼び出す。原資料の読取・採番・二市場の結合・確定足の公開時刻は00154と同じにする。

1. 全通知の順序、判断原行・時刻、担当、売買、新規/返済、枚数、親番号、Ticket、固定幅、境界と理由番号を比較する。
2. 実装固有の注文ID・建玉IDは対応表を作る。返済対象の集合・順序・配賦枚数が同じことを要求し、外部玉へ読み替えない。
3. 追加診断と表示用method名は異なってよいが、当時Observation、固定R、MA、利益予算、親実現金額、残玉段階を比較する。
4. 通知原行の次以降の正常BBOへ全量約定し、各Fillの原行・時刻・数量・価格・返済粗損益を比較する。同原行・異常気配の約定は禁止する。
5. 独立ロット台帳から返済損益・末尾含みを計算し、実保有と予約を合計した片方向10枚上限も検査する。
6. 完了場の残玉・未約定ゼロ、途中場の残玉・含み・未約定の通知対応を確認する。全通知件数・約定件数も一致させる。
7. 対象の52場を最大4並列で処理するが、各場のFeatures・Portfolio・約定台帳は共有しない。出力は新規作成専用で、既存結果を上書きしない。

金額の許容差は絶対値1e-7円未満。表示理由の文言とJSONキー順は比較しない。売買理由番号の変換は現時点で行わない。

## ライブ固有の人工反証

- 初回注文の部分約定中に起動用枚数を仮決めしない。注文完了又は取消確定後の実約定合計をq0とし、完了前のピークは持ち越さない。
- 実手数料は会計に残し、保護判定は研究と同じ粗実現＋清算含みで行う。部分利確の二重計上、追加後のq0やピークの初期化を拒否する。
- `Advance` と鮮度不足の `ObserveWithFreshness` は、新たなS01保護返済目標を作らない。復帰後に回復していれば過去の床割れから注文を作らない。
- 鮮度のある観測で既に発注判断まで成立した返済は、未送信・送信済み・結果不明を問わず意思を維持する。後の回復を理由に判断を取消さない。
- 影の予約・約定・発注は実口座へ流さず、実側の新規許可とは独立して進む。影の順序は「前行までの予約約定→当行の影判断→実側判断」。
- 同HoldIDの部分約定は同一親・注文・Ticketの場合だけ加重平均へ集約する。他の所有玉を混ぜない。
- Dump/Restoreの整合性、起動・時間枠切替時の新規Portfolio、旧標準設定の移行と利用者の明示D07維持を確認する。

## 実行口

```text
go run . -manifest ../inputs155.json -registration ../登録受領155.json -expected-first ../../d07_154/results_go -expected-second ../../d07_154/results_round2 -out ../results
```

`登録受領155.json` の `registered=true` と `returncode=0` を必須にする。結果が一致しても、新しい期間で収益性が確認できたとは扱わない。大口注文・滑り・実mini板・部分約定の収益同値を証明する検査ではない。
