# 統合追試コードの独立レビュー

対象は`integrated_followup.py`、`replay_parts.py`、`exit_integration.py`と入力窓口のコードのみ。追加Nightの原本・入力内容・損益・成果は読んでいない。経済実装は変更していない。

設計の対応関係は妥当である。旧中央12に対して入口の**主方向窓だけ**0.8／1.2とする24条件で、短期価格窓・相手確認遅延・途中判断・退出の条件は維持する。追加Nightは中央12を全件再生し、結果で幅や候補を選ぶコードはない。全futureの成功を待つため、例外で止まった条件だけを除いて完了にする処理もない。旧単一窓の全時計変更とは変更範囲が違うので、報告でも「主方向窓」と限定する必要がある。

ただし、読取時の版には次の証跡接続の不足がある。凍結・本実行前に親へ通知済み。

| 優先箇所 | 読取時の具体点 | 必要な接続 |
|---|---|---|
| 実入力の指紋 | `freeze`は`new_inputs.pkl/new_features_depth.pkl`を固定するが、実際の`replay.initialize('new')`は`inputs.pkl/features_depth.pkl`を読む | 実際の2入力を固定し、旧Day＋Nightの正確な4キーを要求する |
| 実装と監査の指紋 | `replay_parts.py`、入口・B00/B01生成器、旧会計依存などが直接の固定リストにない。人工JSONは真偽だけ読む | 独立監査固定と既存入力監査の全参照SHAを検証して結合。開始・終了の両方で再照合する |
| 旧Day校正 | 12×2入力の実15結果指紋は比較するが、元10入力列・悪化品質・短縮影／通常影の指紋を照合していない | 全列と品質を旧窓口へ照合し、保存済み中央12の実・影・通常影を結ぶ。校正元台帳も固定する |
| 完備の証拠 | `complete`は合計件数と成功一覧のみ。保存成果SHAや厳密なID／キー集合を持たず、前段完備は真偽だけ参照する | 24×26／12×2の一意集合、因果・校正件数、各4成果の指紋、前段完備と元固定の関係を要求する |
| 因果検査の意味 | `integration.causal_check`は生成済み10列を変更し、通常影・短縮影・許可・注文を再生成する。`new_signal_check.py`は入口のみ再生成する | 注文経路の因果と、原素材からB00/B01を再生成する入力因果を区別。後者を追加Nightについて主張する場合は別証跡を接続する |

`F50_NONE`は旧方針の`good_id=B00`を保ち、復元モードだけを`none`へ変える。したがって現在の`new_columns`が回復列にもB00を渡すこと自体は旧`columns`と一致する。回復列を使わないことと、入力列を勝手に0へ変更してよいことは別である。日中校正に全10列の照合を加えれば、この契約も直接確認できる。公開元はrawseqではなくready行で、元B00/B01の`source_row`をそのまま渡すコードになっている。

新Nightの位置付けは「rootが既存5方式の結果を既読、部品担当は未読、旧13で選んだ方式を追加照合」であり、完全未見としない記述が適切である。新Nightで選ばない規則と、すでに読まれた区間を未見と呼ばない説明は維持する。

## 修正後の限定再読取

親が指摘対応後に初めて凍結した版を、価格・損益を読まず再確認した。実使用のmerged入力、実ロードされたwork内実装と旧固定依存、開始／終了SHA照合が追加されている。旧Dayの10列・悪化品質・実15指紋・短縮影と通常影の各10指紋、中央校正元の別固定、各4成果SHA、条件集合・各入力数・因果数・校正数の検査も接続された。これらの修正箇所に重大な不整合は見つからなかった。

追加の`new_mid_signal_check.py`はB00/B01の原素材から切断・未来変更・反射・同秒順を再生成し、方向だけでなく公開元行・公開イベント・品質を比較するため、先の入力因果の不足を補う内容になっている。ただし読取時の凍結追試コードからは、この追加監査の成功・4一意行・実装／入力SHAを必須条件としてまだ照合していない。凍結コードは変えず、新Night開始前の別証跡へこの監査を結ぶことを親へ通知した。監査用の新入力と実使用merged入力のNight部分の関係も、元抽出監査が持つ4ファイルSHA又は直接一致で接続すればよい。

これはコードの限定読取であり、旧24追試の完了や新Night経済成績の監査ではない。新Night結果は引き続き未読。

`launch_new_integration.py`の追加版もコードだけで確認した。4信号の一意集合・成功旗、素材と実使用merged入力の再帰一致、特徴DataFrame一致、開始前後の前提一致、凍結再生の別プロセス起動は妥当である。残る補強点として、SHA辞書の必須キー集合（実装3・入力2）、元抽出証跡の4pickle包含、素材2キーがNightの両銘柄であることを明示要求するよう通知した。空のSHA辞書は現在のforだけでは拒否されないためであり、経済仕様の変更を求めるものではない。

その後の`launch_new_integration.py`で、上記の実装3・入力2・抽出4pickleの厳密キー集合とNight両銘柄キーの要求が追加されたことをコードで確認した。この欠落拒否の指摘は解消している。

## 初期化補完の限定読取

親から、追加Night再生は9条件が成功し、A0の3条件だけ旧Day校正時の参照辞書未初期化で止まったと通知された。失敗後の新規`new_integration_recovery.py`をコードだけで確認した。変更はworkerで正式な`integration.initialize()`を呼んだ後に元`initialize('new')`を呼ぶことだけで、凍結済み`evaluate`・`inspect`・売買・信号・12仕様を変更していない。

復旧側は元固定、中央校正元、入力前提を結び、全12を再実行する。成功済み9条件の4成果ずつのSHAを前提に保存し、再生後に36成果のバイト不変を要求する。12条件×2入力、各2因果・2旧Day校正、全出力指紋、実装と前提の終了後不変を満たして初めて完備を書き出す。新しいmodule集合で元`freeze()`を作り直す処理もなく、重大な残存不整合は見つからなかった。

これは復旧手続きの妥当性の確認であり、復旧実行の成功を先取りした結論ではない。成功済み・未完了を問わず追加Nightの経済結果は読んでいない。
