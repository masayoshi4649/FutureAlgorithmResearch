# 検証した規則を注文APIへ移すときの対応

今回実行したのは保存データ上の注文シミュレーションであり、実口座への発注はしていない。方向計算・状態更新は機械的に実装でき、LSTMは不要。P03だけ過去60組の終値から局所AR(1)を逐次推定する。

| 検証した動作 | AGENTS.mdの手法との対応 | 追加で必要な管理 |
|---|---|---|
| 信号後に直ちに入る「成行相当」 | 新規の`market`は表にない。成立可能な`limit`/`stop`条件による新規発注に相当する抽象モデル | 登録後の条件監視と実約定の通知。今回の成行新規を`method=market`へそのまま置換しない |
| 反発・反落を待つ新規 | `trail` | 条件作成時のATRを固定、期限切れ取消、実約定前の重複抑止 |
| 固定価格を越えた新規 | `stop` | 有効期限と反対条件の取消・照合 |
| 初期損切り＋利確、または追跡返済 | `ifd`/`ifd_oco`と返済側の`stop`/`limit`/`trail` | 実約定した数量だけ返済条件を設定、幅変更時の旧条件取消と照合 |
| 一部利確と残りを追跡 | 複数の新規・IFDと脚別返済 | 建玉番号ごとの数量と返済済み数量を管理する |
| 同時両建て・利益脚のみ返済 | 買いと売りの別注文、脚別のIFD相当 | 両脚の数量・費用・含み損と合算損失を管理。一方しか約定しない場合も扱う |
| 上下の逆指値の早い方だけ採用 | **表のOCOではない**。表のOCOは同じ売買方向に限られる | クライアント側で逆向き２条件を監視し、先行発注後に他方を取消・照合。競合や取消遅延に備えた残数量処理が必要 |
| グリッド・順張り追加・在庫補正 | 複数の`limit`/`stop`条件と脚別返済 | 総枚数の予約枠、約定数量の共有、在庫に応じた取消・再設定、全体損失時の一括返済 |
| セッション終了・建玉全体の損切り | 各建玉へ返済`market` | 未成立新規取消→返済要求→約定照合→残玉再処理の順序が必要 |

API表だけでは、条件登録・取消の遅延、条件成立後の発注価格、サーバーの更新周期、部分約定の通知形式は確認できない。今回の次行・２行後・次の異なる約定時刻の比較はその感度をみる代理モデルであり、実システムの遅延を実測した結果ではない。これらを実装済み・実約定保証ありとは表現しない。

逆指値・トレーリング・利益条件の成立価格と約定価格は区別する。約定は後続の実行可能な売買気配で評価する。新規も返済も、設定した幅で必ず損失が止まるとは仮定しない。
