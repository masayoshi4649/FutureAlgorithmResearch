# グリッド再生の形式

最初に `売買結果.json` の `methods` を読む。40 条件を気配・中値参考・待機指値の 3 方式で独立再生した 120 要素である。主条件は `primary=true` の 5 件で、後から利益順位で選び直さない。詳細な事前条件とコード・資料の SHA256 は `売買仕様固定.json` に保存する。

## 金額の読み方

各 `accounts` は 1 銘柄・1 セッションである。

| 項目 | 内容 |
|---|---|
| `gross_profit` / `gross_loss` | 当場に返済した玉の費用前利益 / 費用前損失の正数合計 |
| `gross_pnl` | 上記の差 |
| `fees` | 当場で実行した全新規・返済注文の手数料 |
| `unrealized_start` | 前場末の残玉を返済可能価格で評価した含み損益。次場始値への差を消さない |
| `unrealized_end` | 当場末の残玉の含み損益 |
| `mtm_change` | 期末含み − 前場末含み |
| `net` | 返済粗利益 − 返済粗損失 − 当場全費用 ＋ 含み増減 |
| `closed_net_profit` / `closed_net_loss` | 返済玉に入口・出口手数料を割り当てた利益 / 損失。期間収支とは別の分類 |
| `win_qty` / `loss_qty` / `flat_qty` | 上記の返済玉に基づく累計枚数。保有枚数ではない |
| `drawdown` | 返済可能価格で残玉を含めた資産の最高値からの最大減少幅 |
| `mid_drawdown` | 同じ注文と在庫を中値評価した最大減少幅。中値方式の独立再生とは区別する |
| `max_long_qty` / `max_short_qty` / `max_gross_qty` | 観測行ごとの最大買枚数 / 売枚数 / 両側合計枚数 |
| `max_losing_inventory` | 利益玉と相殺する前の負け玉だけの含み損合計の最大値 |

`summary[symbol]` は全期間、`weeks[symbol][week]` は週別。同銘柄の各場 `net` の合計は全期間と一致する。週末と調査端で平らにするため全期間の含み増減合計は 0 であり、全期間は返済粗損益 − 全費用に一致する。

`pf` と `payoff` は配分手数料控除後の返済玉で計算する。場内の実現利益だけを期間利益と扱わない。証拠金や必要元本は別問題であり、ここでは推定していない。

## 台帳の行番号

`accounts[].orders` は約定した場へ、`accounts[].trades` は返済した場へ格納する。列名は `meta.order_columns` / `meta.trade_columns` にある。台帳の `*_index` はその銘柄・週の連結済み有効原本行番号であり、`grid/features.py:load_streams()` と対応する。`*_session` は同じ週内の場番号、`*_seq` は各場で 0 に戻る原本行番号である。週全体の `seq` に二分探索してはならない。

`orders` の `kind=1` は新規、`kind=2` は返済、`side=1` は買い注文、`side=-1` は売り注文。`role=0` は格子玉、`role=1` はカバー玉、`role=2` は集約注文に複数の役割が含まれる場合。返済玉の `side` は元の建玉方向である。

`cancellations` は `[判断index,取消index,段番号,枚数]`。新規締切や場跨ぎで取消した予約であり、未約定なので手数料を課さない。

## 注文モデル

- `quote`：条件成立の次有効原本行で買い ask / 売り bid。主集計。
- `mid`：条件成立の次行中値。建値や保護判定も変わる独立再生であり、同じ注文の価格置換ではない。
- `passive`：前行から待機する指値を返済側・執行側の気配が参照ラージ 1 呼値以上通過した場合だけ、待機指値で約定する。逆指値・損切り・全体保護・カバーは次行気配。小型商品の板や待ち順を再現した保証ではない。

全モデルで観測された次行が同じ時計でも原本順に進む。休場の中間価格や飛び越えた段の仮想経路を作らない。場内型で返済前に次場へ移れば安全停止する。週内型の通常場は残玉を引き継ぎ、週末の清算と最終水曜の調査終了清算を別理由で残す。

`backtest.py --freeze-only` は固定記録を作成する。`--run` は固定 SHA の一致を確認して実行する。途中資料の確認用に `load_streams(flatten_study_end=False)` と `replay(..., finish=False)` は調査端の仮想清算を省ける。自然な金曜ナイトの清算は有効なままである。
