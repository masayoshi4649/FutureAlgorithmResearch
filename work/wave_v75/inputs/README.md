# 二銘柄の同期入力

最初に主設定の [同期入力仕様_fresh30.json](同期入力仕様_fresh30.json) を読みます。保存29場・58口座の再利用先、品質、各遅延での利用率を記録しています。続いて [原本時計の再調査.json](原本時計の再調査.json) で全行の時計欄の出現、原本指紋、先頭・途中・末尾の同連番照合を確認します。[同期入力仕様.json](同期入力仕様.json) は変更前の10秒鮮度対照です。

`CurrentPriceTime` は最終約定時刻です。板の更新時刻、受信時刻、銘柄間の共通連番は保存されていません。同期はこの代理時計上での過去対応であり、実際の受信順を証明するものではありません。

主の `sync_fresh30.pkl` と対照の `sync.pkl` は、共に `session → {grid, indices, observation_age, actual_age, both_available}` です。`indices[delay][symbol]` は既存準備入力の行番号で、欠測は `-1`。古さの欠測は `NaN` です。遅延は1・5・15・60秒、基準は5秒です。

共通判断時刻はセッション開始5分後から、安全撤収目安5分前未満までの15秒刻みです。各銘柄について `time < grid - delay` の最新時刻を探し、その同時刻の先頭準備行だけを使います。主は参照期限から30秒超、無効、リセットの行を採用しません。同時刻後続や古い行への救済は行いません。`actual_age` は判断時刻からの古さで、遅延を含みます。鮮度30秒は損益計算前に、[鮮度別の入力十分性.json](鮮度別の入力十分性.json) だけを使って固定しました。

算法からは [core.py](core.py) の `asof_indices(targets, times, valid, reset, max_age=30.)` を呼びます。省略時は対照の10秒なので、主設定では必ず30を指定します。返り値は行番号 `int32` と古さ `float32` の配列です。履歴の始点も同じ関数で参照します。履歴途中のリセットや欠損の連続性は、算法側で別に確認する必要があります。

[prepare.py](prepare.py) の `load_material()` は既存準備配列を読み取りで結合し、`ready, features` を返します。既存の入力・特徴ファイルは複製も変更もしていません。対照と原本時計監査の再生成は `python -X utf8 work/wave_v75/inputs/prepare.py`、主同期の追加生成は `python -X utf8 work/wave_v75/inputs/fresh30.py` です。原本時計の全行調査が完了するまで数分かかります。API取得、実注文、損益の参照は行いません。
