# 運転と保存

## 起動

配布先の商品別フォルダ `TOPIX`・`TOPIXmini`・`NK225`・`NK225mini`・`NK225micro` から、売買する商品を選びます。1フォルダに実行ファイル・`conf`・`docs` があり、1プロセスで1商品だけを売買します。各 `conf/settings.toml` を編集し、実行ファイルを引数なしで起動します。

OS別フォルダ直下には一覧READMEと5商品フォルダだけを置き、共通の実行ファイルや旧 `conf-topix`・`conf-nk` は使いません。例えばTOPIXミニと日経マイクロを起動する場合は次のとおりです。

```text
.\TOPIXmini\sessiontrader.exe
.\NK225micro\sessiontrader.exe
```

Linuxは対応フォルダの `sessiontrader` です。設定は実行ファイルの隣の `conf/*.toml` だけを読み、作業ディレクトリによって切り替わりません。そこに設定がなければ停止します。Go開発環境では `go build -o sessiontrader.exe .` の後に実行してください。`go run .` は一時実行ファイルの隣に `conf` がないため使いません。SQLiteは純Go実装で、MinGW・Cコンパイラ・外部SQLiteサーバーは不要です。

`[startup]` の `action="run"` が通常運転、`"check"` は設定検査、`"probe"` は読み取り接続検査です。検査を終えたら `action="run"` に戻します。`duration_seconds=0` は連続運転、正数はdryrunでの時間指定停止です。`action="migrate_legacy"` と `legacy_conf` は旧版移行に使います。

`[trading]` の `dryrun=true` が仮想運転です。**実注文は `action="run"`・`dryrun=false` で有効になります**。`action="probe"` は実注文設定でも注文・取消を送りません。

`[market]` で発注商品と片方向上限を指定します。新規配布ではTOPIXミニ10枚、日経mini10枚、日経micro20枚、両ラージ2枚です。日経はTG04、TOPIXはT06/T04で、全商品 `dryrun=true` から始めます。既存配布の枚数・dryrun等は保持するため、実ファイルも確認してください。新手法の配分・途中起動・設定切替は[TG04とPG04](TG04とPG04.md)を参照してください。

複数商品を動かす場合は、それぞれの実行ファイルを起動します。既存商品フォルダの実設定・実行ID・`data`・`log` は更新時もそのまま引き継ぎます。

判断はどの商品でもTOPIX・日経225のラージを参照します。商品ID・限月・立会時間はcontrollerから取得します。旧版で複数商品を有効にした設定のままでは起動できません。旧状態を使う場合は[仕様の移行手順](仕様.md#旧版からの移行)に従い、旧設定とDBを残して移行します。

## 時間による切替

次の未参加追加・主担当静観は旧T06/T04/U06の構成です。TG04/PG04は担当ごとに異なる入口を使い、夜間の米国開始前後15分は全担当を返済・静観の対象とします。場内返済の時刻は両構成に共通です。

| 項目 | 初期設定 |
|---|---|
| 日中の未参加時追加 | 日本時間12:30以降 |
| 夜間TOPIXの未参加時追加 | 日本時間で冬翌01:30・英国夏時間翌00:30以降 |
| 夜間日経の未参加時追加 | 米国開始の30分後。日本時間で冬翌00:00・米国夏時間23:00 |
| 夜間主担当の静観 | 米国現物開始の前後15分。追加担当には適用しない |
| 全担当の場内返済 | APIで取得した立会終了の10分前 |
| 追加の新規期限 | 場内返済のさらに10分前 |

日本の開始・終了・送信可能時間をプログラムで固定せず、controllerの立会情報に従います。米国と英国の夏時間はそれぞれの地域で計算します。タイムゾーン情報を実行ファイルへ同梱し、Windows/Linuxで同じ時計を使います。

時刻は `[schedule]` の `_jst` 項目へ日本時間で指定します。米国基準23:30・ロンドン連動01:30は冬の日本時間で、夏は各地域に従って自動で1時間早めます。昼夜の手法は `[methods]` の `day`・`night` で指定し、静観秒数・追尾幅などはその手法に含めます。配布物では `conf/settings.toml` 内にあります。ソース直下の `conf` では、それぞれ `system.toml`・`algorithm.toml` です。変更後は `startup.action="check"` で起動して検査してください。

## 途中起動・再起動

1. 口座・登録一覧と確定足を取得し、二市場の当場生板を履歴APIで完読します。
2. 生板と足が同じセッション・世代であることを確認し、特徴量を準備します。取得中も生PUSHと口座照合を続けます。
3. 初回起動では過去の売買を作りません。準備後に受信した新鮮な板から発注判断します。
4. 再起動ではSQLiteの実約定済み建玉・未確定注文・戦略を復元します。欠測中の履歴は既存建玉の返済条件を確認するために使い、過去価格での返済約定を捏造しません。

履歴には元の受信時刻がないため、暖機では原価格時計と足の名目公開遅延を使います。実際の取得時刻は別に保存します。ライブ中の足は実受信時刻を使い、未確定足を判断に使いません。

寄り付き前の起動で「採用0行」になるのは、前場の価格を当場の判断へ混ぜないためです。08:45以降の板・確定足は引き続き取り込みます。「履歴同期完了」は通信履歴の同期完了で、売買指標がすべて揃ったことを意味しません。

旧T06とTG04/PG04の基本担当は60本EMAと3本分の傾き、自己60秒・相手追加60秒の公開待機を使います。08:45開始の当場だけを使うため、両市場の方向判定が可能になるのは最短でも概ね09:50です。TG04/PG04の他担当は独立した準備・入口を持ち、この時刻を一律の取引開始時刻にはしません。

画面と市場の `trace.jsonl` へ、既定30秒ごとに「稼働」を出します。参照板・発注商品の最終受信時刻、最終判断時刻、受信・判断の累計行数、保有枚数、待機理由を確認できます。間隔は `runtime.status_seconds` で変更できます。価格時計が不正、口座情報が古い、商品板が未受信といった場合も理由を表示します。

画面は `[稼働/dryrun] NK225micro（参照NK225）` のように、運転モード・発注商品・参照ラージを区別します。`仮想保有 買0・売10枚` はアプリ内の仮想約定台帳であり、実口座に注文・建玉がなくても表示されます。再起動時も保存済み仮想残玉を復元します。実注文モードは `[稼働/live]` と `実約定保有` を表示し、このアプリが所有する約定台帳の残数を示します。JSONLの市場別状態には `dryrun` と `position_source` も残します。新規・返済の画面表示にも `[dryrun]` / `[live]` を付けます。

仮想と実注文は売買条件を共用しますが、建玉・注文・戦略の進行状態を別の保存先へ保持します。`dryrun=false` に切り替えても仮想建玉を実口座へ移したり、仮想注文を実送信したりはしません。実注文用の保存状態がなければ未参加から始め、当場履歴で指標を準備した後、新鮮な受信で条件が成立すれば起動直後でも実注文します。日経の夜間未参加補完もその対象であり、起動から一定時間待つ仕様ではありません。起動時点・保有状態・実約定の結果が異なれば、その後の売買も異なります。

同じ保存先の二重起動に加え、同一OSユーザー・同一一時領域・controller URL・商品・モードの重複もOSロックで拒否します。異なるユーザー・ホスト・一時領域やURL別名間の排他は保証できないため、同一商品を重複運転しないでください。売買設定・商品・上限・アルゴリズム版が保存状態と異なる場合も復元を拒否します。**運転中の設定変更は自動反映しません**。

## 中断・終了

エラー終了時は、停止理由を画面と実行ファイル隣の `log/error.log` に日時付きで残します。設定ファイルの読込に失敗しても記録できるよう、このエラーログの場所は固定です。Windowsで実行ファイルを直接開いた場合は、Enterキーを押すまでエラー画面を保持します。PowerShell・cmdなど既存端末からの実行、標準入出力のリダイレクト、Linuxでは入力待機せず終了コード1を返します。正常終了は確認待ちをしません。ログが書込不能でも、元の停止理由と保存失敗を画面に表示します。

例えば片方向上限20枚で保存した後、設定を10枚へ変更すると、`market.max_per_side: 保存=20枚 / 現在=10枚` と対象DBを表示して復元を中止します。これは設定と保存状態の不一致であり、データ破損を意味しません。そのDBで再開するには設定を保存時の値へ戻します。枚数変更による既存建玉・戦略の自動移行は行いません。

短い受信断では直ちに全返済せず、新規を止めて再接続します。初期設定の180秒を超えてラージの受信が途絶えた場合は、返済要求を保持します。実返済は上流の接続・口座照合が復旧してから成行で行います。dryrunは新鮮な発注商品の気配がなければ返済済みにしません。

`Ctrl+C` または終了シグナルで新規を止め、未送信の新規判断を破棄し、担当建玉を返済します。終了猶予は初期設定30秒。未返済・結果不明が残れば、異常終了として状態を残します。

場替わりで `session=null` が返っても正常な休場として待ちます。旧場の残建玉や未確定注文を消して新場へ切り替えません。通信停止・市場停止・プロセス強制終了中の約定や場内返済は保証できません。トレーリングはアプリが計算するため、アプリや通信が停止している間は追尾できません。

送信結果不明の注文は再送しません。上流注文番号が分からないままの場合は、ログと実口座を照合して解消する必要があります。所有不明の注文や手動建玉を推測で自分の玉に取り込みません。

未確定注文がないときは、自分の建玉IDと実口座の残数も照合します。食い違いが出れば新規を止め、口座情報の非同期更新を待っても15秒間解消しなければ運転を停止します。別媒体からの手動返済を推測で吸収しません。

## 記録

SQLiteを正本とし、CSV・JSONLはそこから復旧できる出力です。

相対保存先は、その実行ファイルがある商品別フォルダが基準です。別商品用に複製する場合は実行ファイルと `conf` だけを複製し、既存の所有状態を持つ `data`・`log` は同時運転用に複製しないでください。

| 保存先の例 | 内容 |
|---|---|
| `log/error.log` | 異常終了の日時・理由。設定読込エラーも記録 |
| `data/dryrun/topix-mini/market.sqlite` | 原板、受信時刻、履歴世代、確定足準備情報、運転状態 |
| `data/dryrun/topix-mini/TOPIXmini.sqlite` | 判断・送信待ち・上流注文番号・約定ID・所有玉・戦略状態 |
| `log/dryrun/topix-mini/TOPIXmini/2026-10-20_Night_dryrun.csv` | 新規・返済の確認済み仮想約定 |
| 同じ場所のセッション別 `.jsonl` | 約定と判断根拠を含む詳細 |
| 各ログディレクトリの `trace.jsonl` | 判断・台帳更新・運転イベント |

実運転は `live` ディレクトリ、セッションファイル名の `_dryrun` は付きません。実行IDと商品を分けて同名セッションが衝突しない構成です。日経の例は `data/dryrun/nk-micro/NK225micro.sqlite` です。

セッション別のCSV／JSONLは約定記録です。新規・返済がなければ更新されません。受信・判断が動いているかは、画面の「稼働」または `log/{モード}/{実行ID}/market/trace.jsonl` の「稼働」を確認してください。無約定を、受信停止や判断停止と区別できます。

約定記録には日時・売買・枚数・価格・担当・理由・判断ID・上流注文ID・約定IDを記録します。新手法の担当は `core`/`addon`/`episode`、旧手法は `core`/`extra` です。実現損益列は費用前を維持し、標準手数料、新規建玉ID、返済建玉内訳、照合根拠を別列へ追加しました。費用後合計は実現損益から新規・返済の標準手数料を引きます。

raw板はSQLiteに全受信保存し、CSVへ板全量を複製しません。当場履歴は再取得した回も別入力として記録します。履歴取得や保存先変更でディスク使用量が増えるため、保管・バックアップは停止中に行ってください。実玉・未確定注文がある状態でDBを削除すると所有関係を失います。

## モジュールの分担

| 場所 | 役割 |
|---|---|
| `internal/strategy` | 入口・継続・出口・担当別配分。外部APIを呼ばない |
| `internal/e01` | 日中の基準判断と確定足特徴 |
| `internal/runner` | 履歴準備・時計・受信・判断と約定の接続 |
| `internal/execution` | 送信前保存、上限、担当別返済、部分約定、再送防止 |
| `internal/controller` | 生API・履歴・PUSH接続 |
| `internal/journal` | SQLiteとCSV/JSONL |
| `internal/exitreport` | 異常終了の表示・ログ保存・Windows直接起動時の確認待ち |
| `internal/schedule` | 立会・米英の時間切替 |

戦略を差し替える際は `strategy.Portfolio` の `Observe`（判断）、`OnFill`（約定反映）、`OnOrderDone`（残数量の終了）、`Dump/Restore`（復元）を境界にします。発注受付時点で `OnFill` を呼ばないことが重要です。
