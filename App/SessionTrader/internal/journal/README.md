# SQLite正本と派生ログ

`modernc.org/sqlite` を使い、CGOなしで動作する。`Open(DBパス, ログディレクトリ)` は既存E01の保存APIと同じ呼出し形だが、正本はJSONファイルではなくSQLiteである。既存E01の状態を同じパスへ移して自動変換する機能はない。

DBごとにログディレクトリを分ける。商品別の注文台帳と市場入力DBで同じディレクトリを共有すると `trace.jsonl` が競合する。同じDBの二重運転を防ぐプロセスロックは運転層が担当する。

## 保存範囲

| テーブル | 内容 |
| --- | --- |
| `snapshot` | 最後に確定した復元状態と改訂番号 |
| `trades` | 記録IDが一意な確定約定。担当・商品・判断根拠を含む |
| `sessions` | 約定がなくてもログを用意するセッション |
| `books` | 受信原文、受信時刻、世代、商品、取込元、連番入力ID |
| `events` | 判断・照合・台帳変更・約定確定・入力保存の連番履歴 |

WAL、`synchronous=FULL`、接続1本を使用する。`Save(state, allTrades)` は状態、新たな約定、対応するイベントを同じトランザクションで確定する。既存約定の消失・内容変更・並べ替え・入力内ID重複は拒否する。同じ状態・全約定の再保存は約定や変更イベントを増やさない。

`RecordBooks` はバッチ全体を1トランザクションで保存する。同じ原文でも別受信なら別入力IDを割り当てる。原文の空白も変更しない。途中で失敗したバッチのIDは呼出元へ返さない。入力保存イベントにはバッチの最初と最後の入力IDを記録し、原文そのものは `books` から参照する。

## 復元とログ

- `YYYY-MM-DD_Day.csv` / `Night.csv`：確定約定。仮想運転は拡張子前に `_dryrun` を付ける。
- 同じ基底名の `.jsonl`：CSVと対応する約定のJSON。
- `trace.jsonl`：イベントの連番、分類、セッション、商品、相関ID、時刻、内容。

CSV・約定JSONLは約定追加時に正本から再生成する。トレースは通常、確定済みイベントを追記する。`Open` 時には全て正本から再生成するので、途中で切れたログも修復できる。

`Trade.PnL` とCSVの「実現損益円」は従来どおり費用前の実現額。`Fee` と「標準手数料円」は片道の立会手数料を別に記録する。同じ注文が分割約定した場合、注文累計枚数に対する切捨て額の増分を各約定へ配賦し、注文合計の端数処理を一致させる。旧記録の欠落した費用は0のまま復元し、推定値で過去約定を書き換えない。

新規の `HoldID` と返済の `Closed` は建玉ID単位で追跡する。`ClosedBasis` は仮想指定順による配賦か、口座残数照合による配賦かを示す。複数の返済明細・複数玉の減少が一度に届いた場合、個々の明細と新規建玉IDの対応順を上流情報だけで証明できないため、指定順配賦の根拠を明示する。残玉を返済要求から除外することと、返済されたID集合・合計数量・全体損益の照合は別に行う。CSVの旧18列は保持し、費用・新規建玉ID・返済内訳・根拠の4列を末尾へ加える。

`ProjectionError` は **DBへの確定は成功し、ログだけが失敗した状態** を表す。呼出元は確定済み建玉や約定を巻き戻してはいけない。同内容の再保存または再起動で派生ログを修復できる。それ以外の保存失敗ではトランザクションを巻き戻し、Store自身に未確定の状態を保持しない。

この層は注文APIを呼ばない。「送信前の意図保存」「送信結果不明の照合待ち」「約定の所有関係と部分返済」「戦略への反映位置」は注文管理層が状態に含める。SQLiteへの保存と外部注文送信は単一トランザクションにはできないため、再起動を理由に不明注文を再送しない。

## 確認

`go test ./internal/journal -count=1`

再保存とID重複、SQL挿入途中のロールバック、派生ログ失敗後の確定範囲、CSV引用符、JSONL再構成、同値の別受信、バッチ失敗、同時受信、`Close` なしのプロセス終了後の復元を確認する。実注文APIは使用しない。
